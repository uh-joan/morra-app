## RALPLAN-DR Summary

### Principles
1. **The core is pure — with ports.** Rules, FSM, tempo logic, AI, fusion, fairness, telemetry in a platform-agnostic TS package; all impurity enters via injected ports: `Clock`, `RandomSource`, `TelemetrySink`, `PlayerModelStore`. A JSON conformance corpus (inputs → verdicts/transcripts/minimax distribution) is the portability hedge for any future non-TS port.
2. **Recognition is untrusted input, and the rules correct it.** Recognizers emit ranked hypotheses with confidence + timestamps; core fusion applies the preset-derived legality filter **`call − fingers ∈ [minOpponentFingers, maxOpponentFingers]`** (micatio: `call ∈ [f+1, f+5]`, 25 legal pairs) to reject, rescue, early-accept, or re-throw. Invariant: fusion never emits a pair the rules engine rejects. Buttons are the only real fallback.
3. **Tempo is the product, and there are TWO anchors, never one.** One `AudioContext` and one `getUserMedia` owner (`platform-web`, audio *and* video). The 8-tap round-trip `Δ_user = outputLatency + Δ_human + inputLatency` conflates machine and human terms, so it must be decomposed using the synthetic loopback (which measures `Δ_machine = outputLatency + inputLatency` with no human): `Δ_human = Δ_user − Δ_machine`. Then:
   - **`T_beatAudible = perf(scheduledBeat) + outputLatency_est`** anchors **ALL presentation events** (windup, hand-enters-frame, vocal attack, pinned reveal). Fallback chain for `outputLatency_est`: `ctx.outputLatency` → `baseLatency` → loopback-derived (support probed in S0.4).
   - **`T_expectedInput = T_beatAudible + Δ_human`, expressed in the CAPTURE timestamp domain** — anchors **only the capture window**, centered where the player's input actually lands. The recognizers stamp from rVFC `mediaTime` and the AudioWorklet ring buffer, which are **already capture-referenced: input latency must NOT be re-added** (R5). The 8-tap channel and the loopback channel **must share the same input path** (or per-channel input latency is measured separately) so `Δ_human = Δ_user − Δ_machine` doesn't silently absorb a device difference.
   A player's anticipation bias must shift the window, never the character's performance. `getOutputTimestamp()` mapping re-read every beat and on every resume.
4. **Fairness is a verifiable transcript — with a visible trust anchor.** Two-phase commitment (machine publishes `H(S)` **first**, player nonce `N` arrives **after**, per-throw randomness `r_i = HMAC(S, N‖i)`); the match-start commitment also covers `policyVersionHash` and a **hash of the cross-match player-model snapshot**; the policy is a **pure function** of (seed, nonce, index, model-snapshot, history strictly before *i*). **Trust affordances (D3), without which the ordering is unwitnessed**: (a) the `H(S)` fingerprint (6–8 hex) is displayed on the pre-match screen **before** the nonce-producing action; (b) `N` is a **visible player action** — a displayed rolling code the player locks with a keypress and may re-roll; (c) the audit view renders the ordering (`H(S)` shown → `N` locked → throws → `S` revealed), not merely the final consistency check. The transcript **export includes the model-snapshot bytes** (pruned/bounded ≤ 256 KB) so third-party replay is possible — "offline-verifiable" means verifiable by others, not just by us. The schema retains an **optional per-throw commitment field** (unused locally; P2P becomes a mode switch, not a redesign). Honest claims only: (a) one commitment covers the whole match, (b) replay is deterministic and offline-verifiable. Audit copy: "transcript consistent with pre-match commitment."
5. **Characters are content, not code — clip-first, by user decision.** v1 `CharacterRenderer` is clip-based (offline-rendered 3D footage; AI-assisted production pipeline). Real-time Three.js is v1.1. **User signed off 2026-08-08** on the tradeoff: film-quality hands + proves the filmed-actor interface + no GPU contention, in exchange for fixed camera and quantized cadence tiers in v1.
6. **Risk runs the schedule — with a schedule.** Five spikes with numeric kill criteria gate scaffolding; the project schedule below makes the ordering falsifiable.

### Decision Drivers (top 3)
1. **IRL tempo**: perceived simultaneity (pre-beat windup, pinned reveal); **verdict visible ≤ T_expectedInput + 450 ms at w=300, ≤ T_expectedInput + 300 ms at w=150** — anchored to where the player's throw actually lands, which is what the spec's "throw→verdict" measured (R3). The window is **quantized to the authored grid w ∈ {300, 150}** (matching the two reveal-timing clip variants), not continuous; cadence in **fixed tiers 2.0 s → 1.5 s → 1.2 s**, with `playbackRate` (≤ ±15%) fitting clip timing to the chosen beat interval; continuous cadence adaptation is **dropped from v1** (deliberate deviation from the ~1 s source-material tempo, path in Follow-ups).
2. **Recognition reliability**: per-class ≥95% point estimate **and** 95% Wilson CI lower bound ≥90% on the frozen test split, with **per-class n ≥ 150** (≈38 utterances/class/subject across 4 test subjects — at n=80 the two thresholds are mutually unsatisfiable: 76/80 has Wilson lower 87.8%; n≈150 at p̂=0.95 yields lower ≈90.3%, R4); re-throw rate ≤5% over ≥200 throws across ≥5 calibrated players (calibrated = completed 8-tap calibration with σ < 120 ms).
3. **Portability**: web now; mobile, filmed actors, and server-authoritative P2P later without rewriting the core or the renderer/transcript contracts.

### Viable Options
**A — TS monorepo + MediaPipe + on-device KWS + clip renderer (CHOSEN — the fastest laboratory).** The browser is not the best runtime for this product; it is the fastest place to resolve the two existential unknowns (shouted-number recognition; human beat-sync ability). Native advantages (timing authority, on-device speech APIs, phone framing/ergonomics) are a documented migration path hedged by ports + conformance corpus.
**B — Unity/Godot WebGL.** Honest comparison is "offline 3D pipeline + web clip player" (A) vs "engine runtime" (B): A still needs the offline 3D toolchain, but B additionally imposes engine payloads, weaker web ML interop ergonomics, and a worse embed story — while its runtime-animation strength is exactly what clip-first makes unnecessary in v1. Rejected for v1; revisit for v1.1 roster work.
**C — Server-side recognition.** Latency breaks the verdict budget; AV streams off-device; cost. Rejected outright (interview: v1 needs zero streaming).
**D — Native mobile first (Swift/Kotlin).** The spec's long-term target and the antithesis's best runtime: real timing authority, on-device `SFSpeechRecognizer`-class ASR, natural hand framing on a propped phone. **Rejected for v1 on iteration speed alone**: the existential unknowns need hot reload, DevTools, and fake-media e2e; App Store cycles and device builds would multiply the cost of every recognition experiment.

### Round timeline (dual-anchored: presentation on T_beatAudible, capture on T_expectedInput)
1. **Pre-beat**: `r_i` derived; opponent windup starts (T_beatAudible − windupDuration); count-in cue (audible + **visual pulse** — accessibility & Bluetooth hedge).
2. **Beat**: opponent hand enters frame + vocal attack at T_beatAudible; player throws + shouts; capture window `[T_expectedInput − w, T_expectedInput + w]`, w starts 300 ms, adapting per player (see adaptation law below).
3. **Window close (scheduled, fixed)**: opponent fingers legible **exactly at close** (the visual reveal); the character's **number word onset is at close + ε, ε ≥ 50 ms** — strictly outside the buffered window, so its own grammar word can never enter the recognized buffer by construction; reference-signal subtraction of scheduled character audio (we know its buffer and exact contextTime) remains defence-in-depth, mandatory only when speakers (no headphones) are detected. Reveal is **pinned regardless of early-out** — constant verdict timing, zero jitter, zero leak. Early-out (confident + legal before close) is **load-bearing for the latency budget**: incremental recognition starts **at window open** and consumes the buffer as it fills (defined relative to the window, never as an absolute offset — at w=150 an absolute +120 ms start would leave only 30 ms of pre-close compute, R6), so the post-close voice stage fits its ≤70 ms budget at every w; it also reduces re-throws. **Input arriving after an early accept but still in-window is ignored** — mirroring the physical game's anti-adjustment rule; this is an explicit fusion truth-table row.
4. **Verdict visible ≤150 ms after window close**, decomposed and gated per stage: voice-after-close ≤70 ms (with early-out engaged) + fusion+verdict ≤20 ms + first presented frame ≤50 ms (10 ms slack). Totals, anchored to the player's own throw (R3): ≤ **T_expectedInput** + 450 ms at w=300; **≤ T_expectedInput + 300 ms at w=150 for calibrated players** (**USER SIGN-OFF 2026-08-08: constant-450→300 path approved — figures restated against the throw-anchored clock, which is what the spec's "throw→verdict" measured**). Score/health update; next beat per cadence tier. Character reaction audio **must end before the next window opens** at every offered tier.
5. **Re-throw**: "Non visto!" — no reveal, fresh `r` at bumped transcript index, cap 3 then per-channel button offer. Tracked metric.

**Window adaptation law (D7, R2)**: w is **quantized to the authored grid {300, 150}** — matching the two reveal-timing clip variants, since a fixed informative-frame offset cannot serve a continuously moving close under the ±15% rate cap. Promotion 300→150 requires: settled frames in-window ≥ 6 at the narrow width AND ≥ 60 fps measured capture. **The low-end target (30 fps) is capped at w=300 and is therefore outside the ≤300 ms claim by construction (M6).** The ≤300 ms claim applies only to players promoted to **w = 150**.
**Tier feasibility law (D8)**: `w + 150 ms (verdict) + reactionDuration + windupDuration ≤ cadence`, computed live in `core/src/tempo/` from (w, windupDuration, reactionDuration, captureFps); a tier that fails the inequality is never offered. The fast tiers therefore require a narrow window, which requires 60 fps capture — this coupling is by design, not accident.

### React boundary rules (law)
Game state outside React (XState actor/store; `useSyncExternalStore` + narrow selectors); React renders only low-frequency projections; renderers imperative behind `CharacterRenderer` (no r3f); AudioContext/MediaPipe/recognizers are singletons initialized outside the React lifecycle (StrictMode-safe).

## ADR

**Decision.** Web-as-laboratory v1: pure core with four ports; MediaPipe worker-side landmark counting with settled-frame voting; closed-set on-device call recognition (corpus-trained tiny KWS primary candidate, vosk baseline, buttons only fallback); single platform package owning audio+video devices with dual-anchor discipline (T_beatAudible for presentation, T_expectedInput for capture) and a test-mode seam; **clip-based renderer using AI-assisted offline-3D production (user-approved)**, real-time Three.js deferred to v1.1; **two-phase seeded-policy transcript** (H(S) published before player nonce; HMAC per-throw randomness; model-snapshot hash committed; pure policy; per-throw commitment field reserved for P2P); XState v5 with injected clock and lint-enforced timer ban; five-spike risk gate (S0.3 human factors and S0.5 art capability chief among them); 17–18 week schedule.

**Drivers.** Perceived simultaneity + honest latency arithmetic (450→300 ms path); statistically-gated recognition (Wilson CI) + re-throw budget; portability via ports, conformance corpus, renderer/transcript contracts.

**Alternatives considered.** Unity/Godot WebGL (offline-3D + clip player beats engine runtime for v1; payload/embed costs); server-side recognition (latency/privacy/cost — interview mandated zero streaming); native-first (best runtime, worst iteration speed for the existential unknowns — deferred, not rejected forever); per-throw commit-reveal as primary (one match-start commitment + deterministic replay is cheaper locally; per-throw field retained for P2P); WebSpeech (off-device, not cyclable); vosk-primary (read-speech mismatch to shouting); real-time 3D in v1 (aesthetic risk on hands, GPU contention, toolchain gap — user chose clip-first).

**Why chosen.** The two existential unknowns are cheapest to kill in the browser; every seam (ports, renderer contract, transcript schema, conformance corpus) sits exactly where native/P2P migration will cut; art risk is now gated as early as engineering risk.

**Consequences.** v1 visuals are fixed-camera, tier-cadenced clips; a consented 8-subject corpus and a character production line are scheduled costs; the fairness claim is modest and true; migration paths are documented, not accidental.

**Follow-ups.** v1.1: Three.js runtime renderer, roster, cadence tightening toward authentic ~1 s (playbackRate + re-authored tier grids). v2: P2P flipping the per-throw commitment field to server-authoritative mode; filmed-actor packs; dialect voice packs; "the opponent reads your patterns" stats screen.

## Addendum — S0.3-triggered pivot (2026-08-09, USER DECISION)
Real S0.3 testing (single subject, the user, on baseline hardware) triggered the pre-authorized product-shape pivot: **the abstract metronome beat is rejected** ("the beat is not helping, it makes all very difficult"). Findings from instrumented runs: recognition and detection work (words on ~100% of beats after ring-buffer + VAD fixes), but an external click-driven cadence is hostile to play even at 3–5 s. Decision, two layers:
1. **v1 core loop is self-paced ("sync mode")**: the player throws + shouts when ready; the scored skill is hand–voice co-occurrence (|voice onset − hand onset| ≤ 200 ms), with the recognition window anchored to the hand onset instead of a scheduled beat. Device-latency calibration largely cancels in the within-sensor difference; the 8-tap calibration remains relevant only to beat-anchored modes.
2. ~~**The opponent becomes the rhythm (product)**~~ **SUPERSEDED 2026-08-09 (user decision):** opponent-led pacing was proposed and rejected — "the player sets it; might be a good option for a future version." The PLAYER is the sole pacing authority in v1. The opponent character is presentation only (windup/reveal choreography follows the player's throw, as implemented in the Phase-E two-phase reveal); it never leads. This freezes the v1 shape as self-paced and returns the character-art risk to its original, pre-authorized scope. Rival-led rhythm stays in Follow-ups as a possible future mode.
Consequences: S0.3's kill criterion is superseded (beat-sync hit-rate → co-occurrence rate, target ≥85% self-paced); the metronome/beat machinery survives as the scheduling substrate for opponent-led rhythm; cadence tiers become opponent-personality pacing rather than an imposed clock. The tempo/timeline sections above should be re-read through this lens; a consensus re-review of the affected sections is deferred until the sync-mode spike data validates the new shape.
